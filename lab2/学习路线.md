# 基于搭档实现的 Lab2 学习路线

本路线已改为搭档 `1444f66` 版本，建议约 4–5 小时完成。先读 [本机使用说明](本机使用说明.md)，主报告使用 [搭档报告](report/report.md)。

## 1. 运行原版与辨认验证结果，20 分钟

WSL 进入 `ucore-labs/lab2`：

```bash
make
make qemu
make verify
```

找到 `buddy_check: all tests passed; kernel state restored` 和 `slub_check: all tests passed; PMM pages restored`。退出用 Ctrl+A 后按 x。

区分默认 Buddy 内核自检、独立三后端测试、课程评分三件事。当前课程评分 10/20 是选择 Buddy 与 Best Fit 检查不一致；独立驱动中的 Best Fit 实测通过。不要用旧日志的 20/20 回答当前版本的成绩。

## 2. 内存布局和 page_init，35 分钟

按 `code/kern/mm/memlayout.h` → `pmm.h` → `pmm.c` 阅读，画出 OpenSBI、内核、Page 数组与空闲区。手算 `nbase=524288`、默认 `npage=557056`、描述符数 32768。说明为什么 `Page*`、PA、VA 和 PPN 不能混用。

本机默认空闲区从 `0x804d6000` 开始。对照代码解释 end、数组大小向上对齐、空闲结束向下对齐以及保留状态初始化。搭档版本内核包含较多静态元数据，布局与旧版不同。

## 3. First Fit 与 Best Fit，35 分钟

读 `default_pmm.c` 四个管理函数，再读 `best_fit_pmm.c`。画出 6 页块与 3 页块处理 2 页请求的差别，解释等长时低地址优先、精确匹配提前退出、余块拆分和双侧合并。

理解 `PG_property` 是空闲块头标记，`property` 是块长。查阅独立驱动如何选择 `best_fit_pmm_manager`，不要再使用旧版的 `PMM=best_fit` 编译开关。

## 4. Buddy：重点理解所有权与部分释放，60 分钟

读 `buddy_pmm.c` 的 `buddy_state`、`buddy_allocation`、owner 数组，再读分配与释放。

先画出幂次取整、按阶拆分、物理页号 XOR 找伙伴。再追踪申请 5 页实际占 8 页时的 `requested=5`、`span=8`、`live=5`。解释为什么尾部额外 3 页要保留到最后一个请求页释放后再归还。

跟着 `buddy_check_non_power_two` 画出：释放原分配中间页和头页 → 头部被新分配复用 → 释放旧分配剩余页。重点说明独立 allocation record 与 owner 数组怎样避免把复用头页当成旧块身份。

这版支持部分释放和部分相邻分配范围释放，不能套用旧版“只允许整块配对释放”的说法。再读 kernel_state/test_state 的切换，解释为何不拷贝环形链表哨兵、为何自检后需要恢复被借用区域的描述符。

## 5. SLUB：三个接口与两类链表，40 分钟

接口是 `slub_alloc(size)`、`slub_free(ptr)`、`slub_usable_size(ptr)`。先看 `slub.h`，再看 `slub_cache`、`slub_slab`、`SLUB_DATA_OFFSET`。

追踪申请 17 字节：选 32 字节类 → partial slab → 摘对象 → 位图与计数更新 → 满后移到 full。追踪从 full slab 释放一个对象，最后释放整页。

再看大对象的原请求页数，以及失败后如何归还底层资源。区分 usable-size 的小对象类大小和大对象请求大小。读幂等 slub_init、预初始化保护、溢出处理及失败注入专项测试。

## 6. GDB：先搭档存储实例，再本机取指实例，60 分钟

先读搭档 `report/gdb_test_1.md` 和 `report/evidence` 的存储指令记录，理解宿主 GDB 调 QEMU、RISC-V GDB 调内核。

本机运行：

```bash
make trace
```

读取 `validation/2026-10-25` 中三份新日志。手算本机实例：satp `0x800000000008020b` → 根表 PA `0x8020b000` → VPN[2]=511 → PTE PA `0x8020bff8` → PTE `0x200000cf` → VA `0xffffffffc02000d6` 对应 PA `0x802000d6`。

解释为什么根级叶项无需走完三级、为什么 QEMU 查表函数只返回页基址、为何填入的是 4 KiB 软件 TLB 项。找到首次无效 tag、refill 后的 tag，以及后续 next 跳过 refill 的命中分支。

本机编译器和搭档不同，断点地址应从当前 ELF 重新读取；保留的搭档日志是他的现场证据。

## 7. 脱离报告口述，20 分钟

用自己的话回答：PMM 策略如何注册？为什么默认是 Buddy？owner 与 allocation record 各管什么？部分释放后 padding 何时归还？SLUB 为何要 partial/full？TLB miss 与页故障有什么区别？哪些证据属于当前版本？当前评分为什么 10/20？

最后读 [问题清单](问题清单.md)，了解哪些事项仍保留原状。小组分工表继续留空，后续再填写。
