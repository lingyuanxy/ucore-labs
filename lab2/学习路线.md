# Lab2 学习路线

建议分两次学习，共约 4–5 小时。先取得自己的运行体验，再读实现，最后脱离报告口述。所有命令均在 WSL Ubuntu 的 `lab2` 目录运行。

## 第 1 步：亲自跑通，20 分钟

```bash
make
make qemu
```

找到 `memory management: best_fit_pmm_manager`、`check_alloc_page() succeeded!` 和 `[SLUB] ... PASS`。退出 QEMU：Ctrl+A，松开后按小写 x。

再运行 `make grade`，确认 20/20；运行 `make PMM=buddy qemu`，确认 `[Buddy] ... PASS`。注意评分脚本检查的是默认 Best Fit，Buddy 有单独的启动检查。

学完应能解释：交叉编译器生成什么、QEMU 模拟什么、为什么命令放在 WSL 终端、为什么切换 PMM 后输出会改变。

## 第 2 步：画出内存布局，35 分钟

按顺序读 `memlayout.h` → `pmm.h` 的地址转换函数 → `pmm.c:page_init`。

在纸上画出：OpenSBI、内核、Page 数组、空闲页区。手算以下数值，再用启动日志核对：

1. `0x80200000` 加映射偏移得到什么 VA？
2. 128 MiB RAM 有多少物理页？为什么 `npage` 是 557056，而描述符数是 32768？
3. `pages` 为何放在 `ROUNDUP(end, 4096)`？数组占多少页？
4. `pa2page` 和 `page2pa` 为什么要减/加 `nbase`？

通过标准：不用看代码，能区分 PA、VA、PPN、Page 指针；能解释为什么不能从内核末尾直接开始分配。

## 第 3 步：理解 First Fit 和 Best Fit，40 分钟

先读 `default_pmm.c` 的四个核心函数，再读 `best_fit_pmm.c`。每读完一个函数，自己画出链表变化。

练习：低地址有 6 页块，高地址有 3 页块，请求 2 页。分别画出 First Fit 与 Best Fit 的选择和余块。再设计一次释放，同时触发前后两侧合并。

重点解释 `PG_reserved`、`PG_property`、`property`、`nr_free` 各自的含义；不要把空闲块头标记当成每页空闲标记。

通过标准：能解释“Best Fit 为什么仍有碎片”，以及选块、拆分、插入、合并四件事如何配合。

## 第 4 步：理解 Buddy，40 分钟

读 `buddy_pmm.c` 的初始化、分配、释放，再看 `buddy_check`。画出一个 16 页块申请 3 页的拆分过程。

自己计算页号 0–7 的 order-0 伙伴，再计算 order-1 的伙伴。确认页号 1 与 2 虽相邻，却不是伙伴。

必须回答：申请 3 页实际占多少？为什么释放仍传原请求 3？为什么伙伴用绝对物理页号 XOR，不能随便对 Page 指针地址 XOR？非对齐的初始区间为什么需要拆成多个块？

通过标准：能手画拆分和递归合并，并说明测试为何专门使用 31 页非对齐区域。

## 第 5 步：理解 SLUB，35 分钟

读 `slub.c` 的头部结构、`new_slab`、`kmalloc`、`kfree`，最后看测试。

以 `kmalloc(17)` 为例说明：选择 32 字节大小类 → 取 partial slab → 摘空闲对象 → 更新位图与使用数。再说明释放最后一个对象时如何把整页还给 PMM。

用 `kmalloc(8193)` 解释大对象路径，并比较下层使用 Best Fit 和 Buddy 时实际占用页数的差异。头部记录的是原请求页数，释放必须遵守底层约定。

通过标准：能区分页分配器与对象分配器，说明内部碎片、对齐、头部开销和空 slab 回收。

## 第 6 步：亲自调试地址翻译，60 分钟

先运行自动取证：

```bash
python3 tools/trace_mmu.py
```

然后读 `evidence/guest-kernel.txt` 和 `evidence/host-mmu.txt`。对照 `entry.S`，找出写 satp、刷新 TLB、建立虚拟栈和跳到 C 入口的指令。

手算报告中的这条翻译：

```text
VA 0xffffffffc02000d6
satp 0x8000000000080205
根表 PA 0x80205000
VPN[2] 511
PTE 地址 0x80205ff8
PTE 0x200000cf
最终 PA 0x802000d6
```

再读 `evidence/host-tlb.txt`，找到首次无效 tag、填充后 tag、下一次 `next` 跳过 refill 分支的三组记录。

想交互操作时，先用两个 WSL 终端运行 `make debug` 和 `make gdb`，在来宾 GDB 中用 `hbreak *0x80200000`、`hbreak kern_init`、`continue`、`info registers pc satp`、`stepi`。观察 QEMU 源码时，用普通宿主 GDB 执行 `evidence/host-mmu.gdb` 中的命令；不要把 x86_64 QEMU 交给 RISC-V GDB 调试。

通过标准：能解释“Sv39 为什么本次只读一层”“函数返回的 PA 为什么少了 0xd6”“Bare 模式为什么 QEMU 仍会走软件 TLB”“为什么有些 C 局部变量 optimized out”。

## 第 7 步：模拟答辩与整理，20 分钟

关掉报告，用自己的话回答：

1. 从 `kern_entry` 到 `kmalloc`，整条初始化链是什么？
2. 为什么内核、OpenSBI、Page 数组不能分配出去？
3. 哪个变量表示空闲页总数？哪个字段表示块长？
4. First Fit 与 Best Fit 哪一步不同？
5. Buddy 为什么只能与同阶伙伴合并？
6. SLUB 为什么能减少小对象占满一页的浪费？
7. satp 存的是根表 VA、PA，还是 PPN？
8. 根级大页和 QEMU TLB 的 4 KiB 记录有什么区别？
9. TLB 未命中一定是缺页异常吗？
10. 哪些现象来自实际日志，哪些是根据源码解释得到的？

第 9 题的关键：TLB miss 只是缓存中没有映射；页表合法时可以填充后继续，只有权限、映射等检查失败才可能产生相应异常。
